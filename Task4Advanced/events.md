# Каталог доменных событий

## Общая часть контракта

Все приведённые события имеют версию `1`. Обязательные поля конверта:

| Поле | Значение |
| --- | --- |
| `event_id` | Уникальный UUID события; не меняется при повторной доставке |
| `event_type` | Имя из каталога ниже |
| `event_version` | Версия схемы контракта |
| `occurred_at` | Время факта в UTC, ISO 8601 |
| `source_context` | Код контекста-источника |
| `correlation_id` | Технический ID процесса для трассировки, без персональных данных |
| `payload` | Минимальная полезная нагрузка по таблице ниже |

`payload` не содержит ФИО, диагнозов, назначений, снимков, текстов заключений
и содержимого исследований. В закрытых медицинских событиях допускаются
только необходимые ID и ссылки-идентификаторы объектов. Это не публичные
URL и не токены доступа: файлы читаются отдельно с сервисной авторизацией.

Поля `*_id` — строковые идентификаторы, `event_id` — UUID; версии сущностей —
целые числа. `quantity` — положительное количество в указанной единице.
Для E01 начальный статус — `active`, для E13 допустимы `available`,
`maintenance`, `unavailable`.

Суммы `amount_minor` передаются целыми числами в минимальных денежных единицах,
валюта `currency` — кодом ISO 4217. Версии сущностей — целые числа,
монотонные в пределах соответствующего агрегата.

## События и подписчики

| ID / событие | Источник и семантика | Подписчики и реакция | Минимальный `payload` |
| --- | --- | --- | --- |
| E01 `PatientRegistered` — зарегистрирован пациент | PAT: регистрация подтверждена | CARE: обновляет локальную проекцию ID и статуса пациента | `patient_id`, `status`, `patient_version` |
| E02 `StudyRequested` — назначена обработка исследования | CARE: исследование с исходным файлом готово к передаче в ИИ | AI: создаёт идемпотентное задание анализа | `study_id`, `input_object_id`, `model_version`, `study_version` |
| E03 `AIAnalysisCompleted` — исследование обработано ИИ | AI: обработка завершена, результат сохранён в закрытом медицинском хранилище | CARE: связывает результат с исследованием и меняет его состояние | `task_id`, `study_id`, `result_object_id`, `model_version`, `task_version` |
| E04 `ClinicVisitCounted` — учтено посещение клиники | CARE: приём завершён; подготовлен отдельный обезличенный факт для отчётности | ANA: увеличивает число посещений по клинике и периоду с дедупликацией | `clinic_id`, `count` (всегда `1`) |
| E05 `ServiceChargeCreated` — создано начисление за услугу | CARE: подтверждено начисление после оказания услуги | BILL: создаёт позицию черновика счёта, не дублируя начисление | `charge_id`, `billing_party_id`, `clinic_id`, `amount_minor`, `currency` |
| E06 `InvoiceIssued` — выставлен счёт на оплату | BILL: счёт проверен и выставлен плательщику | ACC: готовит платёжное поручение, не списывает деньги автоматически; ANA: обновляет финансовую витрину | `invoice_id`, `billing_party_id`, `clinic_id`, `amount_minor`, `currency`, `invoice_version` |
| E07 `LoanAgreementCreated` — создан кредитный договор | LEND: создана запись договора с начальными условиями | ACC: готовит данные для обслуживания договора; ANA: учитывает созданные договоры отдельно от выданных кредитов | `loan_id`, `bank_customer_id`, `amount_minor`, `currency`, `term_months`, `status` (всегда `created`), `loan_version` |
| E08 `AccountOpened` — открыт банковский счёт | ACC: счёт создан и активен | LEND: обновляет проекцию доступных счетов клиента; ANA: обновляет финансовые показатели | `account_id`, `bank_customer_id`, `currency`, `account_version` |
| E09 `PaymentCompleted` — исполнен платёж | ACC: операция действительно исполнена и отражена на счёте | BILL: учитывает оплату при наличии `invoice_id`; LEND: учитывает платёж при наличии `loan_id`; ANA: обновляет показатели платежей | `payment_id`, `account_id`, `amount_minor`, `currency`, `invoice_id` или `loan_id`, `account_version` |
| E10 `EmployeeHired` — принят сотрудник | HR: кадровое оформление завершено | INV: готовит заявку на выдачу имущества без автоматического уменьшения остатков; ANA: обновляет кадровую витрину | `employee_id`, `department_id`, `hire_date`, `employee_version` |
| E11 `InventoryItemIssued` — выдано имущество | INV: выдача подтверждена и остаток изменён | HR: обновляет проекцию закреплённого имущества; ANA: учитывает движение запасов | `operation_id`, `stock_item_id`, `employee_id`, `quantity`, `unit`, `stock_version` |
| E12 `PharmaDeliveryAccepted` — принята фармацевтическая поставка | PHARM: приёмка строк поставки подтверждена | INV: приходует строки поставки с защитой от повторов; ANA: учитывает объём поставок | `delivery_id`, `order_id`, `warehouse_id`, `lines[]` (`line_id`, `sku`, `quantity`, `unit`), `order_version` |
| E13 `DeviceStatusChanged` — изменён статус оборудования | EQUIP: зафиксирован допустимый переход эксплуатационного состояния | CARE: обновляет доступность устройств для планирования; INV: обновляет справочную проекцию статуса актива без изменения количества; ANA: считает доступность оборудования | `device_id`, `clinic_id`, `status`, `device_version` |

Для E09 заполняется ровно одна ссылка назначения: `invoice_id` или `loan_id`.
Потребитель игнорирует назначения другого типа. Оплаты и выдача денег
выполняются только по отдельно авторизованным банковским командам;
`InvoiceIssued` и `LoanAgreementCreated` не являются разрешением на списание.

E04 и E05 — два разных события одного завершения приёма. Они фиксируются
в outbox вместе с изменением `Visit`, но предназначены разным потребителям.
В E04 нет `patient_id`, `visit_id`, названия процедуры и медицинских сведений.
Его `event_id` и `correlation_id` создаются отдельно от закрытого медицинского
процесса; связь остаётся только у CARE. E05 содержит финансовые данные
начисления и не доступно аналитическому потребителю.

## Топики и доступ

| События | Топик | Доступ |
| --- | --- | --- |
| E01 | `medical.patients` | PAT публикует, CARE читает |
| E02 | `medical.studies` | CARE публикует, AI читает |
| E03 | `medical.ai` | AI публикует, CARE читает |
| E04 | `clinic.operations.visits` | CARE публикует, ANA читает |
| E05 | `clinic.billing.charges` | CARE публикует, BILL читает |
| E06 | `corporate.billing.invoices` | BILL публикует, ACC и ANA читают |
| E07 | `finance.loans` | LEND публикует, ACC и ANA читают |
| E08 | `finance.accounts` | ACC публикует, LEND и ANA читают |
| E09 | `finance.payments` | ACC публикует, BILL, LEND и ANA читают |
| E10 | `corporate.hr` | HR публикует, INV и ANA читают |
| E11 | `corporate.inventory` | INV публикует, HR и ANA читают |
| E12 | `pharma.deliveries` | PHARM публикует, INV и ANA читают |
| E13 | `equipment.status` | EQUIP публикует, CARE, INV и ANA читают |

Здесь `medical.*` — обозначение всех медицинских топиков по префиксу,
а не публичный канал. У ANA нет прав чтения этих топиков и медицинских
хранилищ. Финансовые и кадровые идентификаторы доступны только в ограниченных
наборах соответствующих подразделений. Общие отчёты используют согласованные
агрегированные показатели; права на наборы и строки проверяются порталом.

## Доставка и изменение контрактов

- Kafka key — ID агрегата-источника; для E04 используется `clinic_id`.
  Порядок гарантируется только внутри партиции. Версия сущности защищает
  потребителя от применения устаревшего изменения.
- Доставка at-least-once: обработка может повторяться. Потребитель проверяет
  `event_id`, а INV при поставке дополнительно проверяет `delivery_id + line_id`.
  Подтверждение Kafka offset выполняется после успешной локальной записи.
- Контракты хранятся в Schema Registry. Совместимость проверяется до выпуска;
  несовместимое изменение получает новую версию и переходный период.
- Временная ошибка обрабатывается ограниченными повторами. После исчерпания
  попыток или при ошибке контракта в DLQ сохраняются ID, код ошибки и ссылка
  на исходное сообщение. DLQ — очередь необработанных сообщений; она имеет
  те же ограничения доступа, что исходный поток, и не хранит медицинские документы.
- Для восстановления проекции применяется повторное чтение сохранённых
  событий или сверочная загрузка из источника. Срок хранения событий
  должен покрывать согласованное время восстановления.
