# Bounded contexts и агрегаты

## Агрегаты, ключи и инварианты

| Контекст | Корень и ключ | Граница агрегата | Инварианты |
| --- | --- | --- | --- |
| PAT | Пациент (`Patient`), `patient_id` | Регистрационные данные и административный статус; без медицинской истории | ID неизменяем; регистрационный идентификатор уникален в контексте; изменения выполняются только разрешённым сотрудником |
| CARE | Приём (`Visit`), `visit_id` | Клиника, ссылка на пациента, время, состояние и начисления за оказанные услуги | Пациент существует в локальной проекции PAT; закрытый приём нельзя закрыть повторно; одно начисление имеет уникальный `charge_id` |
| CARE | Исследование (`Study`), `study_id` | Ссылка на приём, состояние исследования и ссылки на файлы/результаты | Задание создаётся только при наличии исходного файла; результат принимается для своего исследования; завершение фиксируется только при наличии сохранённого результата |
| AI | Задание анализа (`AnalysisTask`), `task_id` | ID исследования, версия модели, состояние и ссылка на результат | Одно сочетание `study_id + model_version` не выполняется повторно как новое задание; успешное завершение требует сохранённого результата; повторное сообщение не создаёт второй результат |
| LEND | Кредитный договор (`LoanAgreement`), `loan_id` | Клиент банка, сумма, валюта, срок и состояние договора | Сумма и срок положительны; создание не означает одобрение или подписание; подписанные условия нельзя незаметно заменить; событие создания не разрешает выдачу денег |
| ACC | Банковский счёт (`Account`), `account_id` | Владелец, валюта, статус, доступный остаток и операции счёта | Списание разрешено только с активного счёта и при достаточном доступном остатке; сумма положительна, валюта совпадает; один `payment_id` не списывается дважды |
| BILL | Счёт на оплату (`Invoice`), `invoice_id` | Плательщик, позиции начислений, сумма, валюта и подтверждённые платежи | Сумма равна сумме позиций; один `charge_id` не включается повторно; после выставления позиции не меняются без корректирующего документа; оплаченный статус требует подтверждённых платежей на нужную сумму |
| HR | Сотрудник (`Employee`), `employee_id` | Кадровый статус и подразделение | ID неизменяем; действующий сотрудник относится к существующему подразделению; кадровый переход должен быть допустимым |
| INV | Складская позиция (`StockItem`), `stock_item_id` | Склад, SKU, единица измерения и доступное количество | Пара `warehouse_id + sku` уникальна; остаток неотрицателен; выдача не превышает доступный остаток; одна операция поступления/выдачи учитывается один раз |
| PHARM | Заказ поставки (`SupplyOrder`), `order_id` | Поставщик, строки заказа и подтверждённые приёмки | Количество по строкам положительно; принятое количество не превышает заказанное; одна строка поставки `delivery_id + line_id` не принимается повторно |
| EQUIP | Устройство (`Device`), `device_id` | Серийный номер, клиника и эксплуатационный статус | Серийный номер уникален; переход статуса допустим; устройство на обслуживании не помечается доступным; новое состояние получает следующую версию |
| ANA | Определение отчёта (`ReportDefinition`), `report_id` | Автор, разрешённые наборы, срезы и фильтры отчёта | Автор может использовать только доступные ему наборы; доступ повторно проверяется при запуске; медицинские документы и закрытые medical.* недоступны |

Платёж в этой модели — операция агрегата `Account`, а не общий агрегат
для банка и BILL. ACC подтверждает факт исполнения, BILL применяет этот
факт к своему `Invoice`. История операций может храниться отдельно физически,
но правила изменения счёта остаются у ACC.

Витрины ANA — проекции событий, а не источники истины по кредитам,
пациентам или остаткам. `ReportDefinition` управляет настройками отчёта;
внутренние события его изменения не нужны для междоменной интеграции,
поэтому в общем каталоге не перечислены.

## Правила интеграции контекстов

- Контекст-источник определяет смысл события и публикует версионируемый
  контракт (Published Language). Потребитель переводит его в свою модель.
- Внешние API фармкомпаний и производителя оборудования проходят через
  антикоррупционный слой (Anti-Corruption Layer) в PHARM/EQUIP. Он преобразует внешние модели
  в команды своего контекста; необработанный внешний ответ не считается
  подтверждённым доменным событием.
- На этапе миграции такие же адаптеры отделяют Camel и SQL Server 2008
  от новой модели. Новая бизнес-логика в DWH не добавляется.
- Изменение агрегата и запись outbox выполняются в одной локальной транзакции.
  Издатель отправляет событие после фиксации. Получатель записывает `event_id`
  вместе с результатом обработки и не выполняет действие повторно.
- Между контекстами допускается задержка согласования. Например, BILL
  помечает счёт оплаченным после `PaymentCompleted`, а до этого показывает
  ожидание подтверждения. Если событие пришло раньше локального документа,
  оно ожидает повторной обработки, а не теряется.
- При приёмке поставки INV обновляет позиции отдельно. Повтор после сбоя
  безопасен благодаря ключу `delivery_id + line_id`: уже учтённая строка
  не увеличивает остаток снова.
